# Customer onboarding (Excel import)

How a new customer's organization structure and employees are loaded into a fresh deployment. Written for the HR
administrator doing it and the engineer supporting them.

---

## 1. Purpose and scope

One customer = one deployment = one database (see `docs/production-readiness.md`). This import fills an **empty**
installation: organizations, departments, jobs, positions and employees, in one workbook, in one transaction.

It is **create-oriented**. Every row declares "create this". A code that already exists is an error, never a silent
update — there is no bulk-edit mode, no upsert and no undo. Later corrections are made in the normal screens.

## 2. What you need

- `onboarding.manage` permission (HR Admin or System Admin).
- The template from **Administration → Onboarding → Download template**. It is generated by the server, so it always
  matches what the importer expects. Do not reuse an older template: each one carries a version, and an unknown
  version is rejected rather than guessed at.

## 3. The workbook

| Sheet | Creates | Key columns |
|---|---|---|
| Organizations | companies / legal entities | `organizationCode`, `name`, `timezone` |
| Departments | department tree | `organizationCode`, `departmentCode`, `name`, `parentDepartmentCode`, `headEmployeeCode` |
| Jobs | job catalogue | `jobCode`, `title`, `level`, `description` |
| Positions | seats in a department | `positionCode`, `title`, `organizationCode`, `departmentCode`, `jobCode` |
| Employees | people | `employeeCode`, `firstName`, `lastName`, `email`, `hireDate`, `employmentType`, `positionCode`, `managerEmployeeCode` |

Rules the file must follow:

- **Do not rename** sheets or header cells. Unknown *named* columns are reported as warnings and ignored; a missing
  required header is an error. Nothing is fuzzy-matched — a mis-mapped column would silently import wrong data.
- **Codes are text.** Leading zeros are preserved (`00123`), and codes are stored uppercase, exactly as the rest of
  the system does.
- **Dates are `YYYY-MM-DD`.** `01/02/2026` is ambiguous and is rejected. A real Excel date cell is read from its
  calendar parts, so a timezone can never shift the day.
- **No formulas** in data cells. A formula is rejected rather than trusted.
- **Blank rows are ignored.** Row numbers in error messages match what Excel shows.
- An employee's department and organization come from their **position** — they are not separate columns, so they
  cannot disagree.

### References may point forward

A row may reference something created later in the same workbook: a department's parent, a position's department, an
employee's manager, a department's head. Sort order does not matter. References may also point at records that already
exist in the system (for example adding a department to an organization that is already there).

## 4. Preview, then import

1. **Preview** uploads the file, validates everything and **saves nothing**: no records, no audit entries, and the
   workbook itself is never stored.
2. You get counts per sheet and, if anything is wrong, a list of problems with sheet, row, field, code and message.
   **Download error CSV** gives the same list to work through offline.
3. Fix the file, preview again.
4. **Import** re-uploads the same file. The server hashes it and refuses (`ONBOARDING_FILE_CHANGED`) if it is not the
   file that was previewed, then re-validates everything *inside the transaction* — the database may have changed
   since the preview.

Because the workbook is never stored, reloading the page means previewing again. That is deliberate: a file full of
personal data should not sit on a server waiting to be imported.

## 5. All-or-nothing

One transaction. A single blocking error means **nothing** is created — not even the organizations that validated. If
row 900 fails, rows 1–899 disappear with it. Concurrent imports are serialised with a PostgreSQL advisory lock taken
only by this operation, so ordinary application traffic is unaffected.

Re-submitting a workbook that was already imported returns the original import record instead of importing it twice
(the file's SHA-256 is the idempotency key).

## 6. What the import does NOT do

- **No login accounts.** Importing employees never creates users, passwords or invitations, and never links an
  employee to an existing account by matching email — that would turn an address into a security binding. Accounts are
  created separately in Administration → Users.
- **No updates** to existing records, no deletions, no undo.
- **No leave history, payroll or attendance data** — those are separate concerns and are not part of this workbook.

## 7. Validation reference

*Structure*: `ONBOARDING_TEMPLATE_VERSION_UNSUPPORTED`, `ONBOARDING_INVALID_WORKBOOK`, `ONBOARDING_MISSING_SHEET`,
`ONBOARDING_MISSING_COLUMN`, `ONBOARDING_DUPLICATE_COLUMN`, `ONBOARDING_UNKNOWN_COLUMN` (warning),
`ONBOARDING_FILE_TOO_LARGE`, `ONBOARDING_TOO_MANY_ROWS`, `ONBOARDING_UNSUPPORTED_FILE_TYPE`,
`ONBOARDING_FORMULA_NOT_ALLOWED`, `ONBOARDING_CELL_ERROR`.

*Values*: `ONBOARDING_REQUIRED`, `ONBOARDING_INVALID_VALUE`, `ONBOARDING_INVALID_DATE`.

*Duplicates and conflicts*: `ONBOARDING_DUPLICATE_IN_FILE`, `ORGANIZATION_CODE_EXISTS`, `DEPARTMENT_CODE_EXISTS`,
`JOB_CODE_EXISTS`, `POSITION_CODE_EXISTS`, `EMPLOYEE_CODE_EXISTS`, `EMPLOYEE_EMAIL_EXISTS`.

*References and rules*: `ORGANIZATION_NOT_FOUND`, `DEPARTMENT_NOT_FOUND`, `DEPARTMENT_PARENT_NOT_FOUND`,
`DEPARTMENT_SELF_PARENT`, `DEPARTMENT_CYCLE`, `JOB_NOT_FOUND`, `POSITION_NOT_FOUND`, `MANAGER_NOT_FOUND`,
`MANAGER_INACTIVE`, `EMPLOYEE_SELF_MANAGER`, `MANAGER_CYCLE`, `EMPLOYEE_NOT_FOUND`, `EMPLOYEE_INACTIVE`,
`DEPARTMENT_HEAD_NOT_IN_DEPARTMENT`.

*Import*: `ONBOARDING_FILE_CHANGED`, `ONBOARDING_VALIDATION_FAILED`, `ONBOARDING_IMPORT_FAILED`.

## 8. Audit and history

Every created record is audited exactly as if it had been created in the UI (`CREATE_ORGANIZATION`,
`CREATE_DEPARTMENT`, `CREATE_JOB`, `CREATE_POSITION`, `CREATE_EMPLOYEE`, plus manager and department-head changes),
because the importer calls the same domain code. One additional `IMPORT_CUSTOMER_ONBOARDING` entry records the batch:
file name, file hash, template version and counts — never row content.

**Administration → Onboarding → Recent imports** lists past imports with counts, who ran them and when. It holds
metadata only: no names, no emails, no workbook.

## 9. Limits and privacy

- 10 MB per file, 5,000 data rows in total, one workbook per request.
- The upload is bounded while streaming; nothing is written to disk and nothing survives the request.
- Logs record counts, a file-hash prefix, the actor and durations — never names, emails or row values.
- The uploaded file must be `.xlsx`; the declared content type alone is never trusted, since the parser has to read it
  as a real workbook with the expected sheets.

Measured locally with 1,000 employees / 100 positions / 40 departments (development laptop, PostgreSQL 18):
55 KB file, preview ~0.1 s, import ~6 s, producing 1,000 position histories and 900 manager histories. Development
figures, not a production guarantee.

## 10. Known limitations

- Create-only: no bulk update, no re-import to change data, no undo.
- No user accounts, invitations or password setup (deliberate — there is no account-recovery flow yet).
- No historical leave, attendance or payroll import.
- One workbook per request, processed synchronously: no background queue, so very large customers should be split.
- The source workbook is never retained; keep your own copy of what you imported.
- Department heads must be employees assigned to that department (the same rule the UI enforces).
- `.xlsx` only — no `.xls`, `.csv` or macro-enabled workbooks.
