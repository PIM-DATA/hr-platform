# Deployment — canonical install path and checklist

One customer = one deployment = one PostgreSQL database. This is the single supported path from a clean checkout to a
running system (Task 46); it was executed end-to-end on an empty database (see the audit document). Every variable is
described in [environment-reference.md](environment-reference.md).

```
PostgreSQL ─┐
            ├─ Node API (loopback :4000, NODE_ENV=production)  ◄── /api/*  ─┐
documents ──┘                                                               ├── TLS reverse proxy (owns TLS, HSTS,
                                          apps/web/dist (static files) ◄── / ┘    web security headers, caching)
```

## 1. PostgreSQL

An empty database and a dedicated login role (no superuser). Developed against PostgreSQL 18; standard SQL only.

```sql
CREATE ROLE hr_app LOGIN PASSWORD '…';          -- from your secret store
CREATE DATABASE hr OWNER hr_app;
```

## 2. Environment

Keep the configuration outside the repository, readable only by the service user (`chmod 600`), e.g.
`/etc/hr-platform/api.env`:

```ini
NODE_ENV=production
DATABASE_URL="postgresql://hr_app:…@db.internal:5432/hr?schema=public"
PORT=4000
CORS_ORIGIN=https://hr.example.com
PUBLIC_APP_URL=https://hr.example.com
TRUST_PROXY=1
COOKIE_SECURE=true
DOCUMENT_STORAGE_DIR=/var/lib/hr/documents
COPILOT_ENABLED=false
APP_VERSION=0.1.0-rc.1
LOG_LEVEL=info
```

The API refuses to start if `NODE_ENV` is missing or not exactly `production`, if any production value is missing or
unsafe (origins, reset URL, cookies, proxy trust, document storage, copilot) — names and reasons are printed, never values.

## 3. Documents directory

```sh
install -d -m 700 -o hr /var/lib/hr/documents
```

Persistent storage, never a temporary path. Create it at install time (an empty root is accepted only while the
database has no documents; afterwards a missing or empty root makes the API not ready instead of being re-created).
It is backed up together with the database in every recovery set — [backup-restore.md](backup-restore.md).

## 4. Build (code generation included)

Supported: Node ≥ 20 with its npm (verified with Node 24 / npm 11).

```sh
npm ci                # exact lockfile install (dev dependencies included: the Prisma CLI and tsx run migrations and ops scripts)
npm run build         # Prisma client generation → packages/shared → apps/api (dist) → apps/web (dist)
```

`npm run build` generates the Prisma client itself (`npm run codegen`); nothing has to be generated by hand. `npm run
typecheck` and `npm test` do the same. The web bundle ships without source maps. A regression guard is available:
`npm run verify:clean-build` (exports the committed tree into a temporary directory, `npm ci`, `npm run build`, checks
the outputs and that no source map is published).

## 5. Migrations — before every start of a new version

```sh
# the Prisma CLI reads DATABASE_URL from the environment; the subshell keeps it out of your login shell
( set -a; . /etc/hr-platform/api.env; set +a; npm run db:deploy )   # prisma migrate deploy — never migrate dev / reset / db push
```

Order is **build → migrate → start**. A failed migration aborts the release.

> Variables exported in your shell **override** `ENV_FILE` (real environment always wins). Do not leave a
> `DATABASE_URL` exported from another environment in the shell you deploy from — the Task 46 drill showed that a
> bootstrap then silently targets the database that was exported, not the one in `ENV_FILE`.

## 6. Bootstrap (first install only)

```sh
ENV_FILE=/etc/hr-platform/api.env BOOTSTRAP_ADMIN_EMAIL=owner@example.com BOOTSTRAP_ADMIN_PASSWORD='…' npm run bootstrap:admin
```

Creates the permission catalogue, the six roles and one System Admin — no sample company, no demo accounts. The demo
seed (`npm run db:seed`) refuses `NODE_ENV=production`. There is no default password.

## 7. Reverse proxy and TLS

TLS is terminated by the reverse proxy, which serves `apps/web/dist` and forwards `/api/` to the API on loopback. Use one
of the reference configurations:

- **Apache httpd 2.4** — [deploy/apache/hr-platform.conf](../deploy/apache/hr-platform.conf) +
  [hr-platform-site.conf](../deploy/apache/hr-platform-site.conf) (verified end-to-end in Task 46, HTTP and TLS).
- **nginx** — [deploy/nginx/hr-platform.conf](../deploy/nginx/hr-platform.conf) +
  [security-headers.conf](../deploy/nginx/security-headers.conf) (equivalent; header parity checked by a test).

## 8. `TRUST_PROXY`

`req.ip` (rate limiting, audit attribution) and `req.protocol` (same-origin check) depend on it. Choose the value that
describes the real path of a request:

| Topology | `TRUST_PROXY` | Why |
|---|---|---|
| A. API reachable directly (no proxy) | `off` | X-Forwarded-* is ignored; a client cannot claim another IP. |
| B. One reverse proxy (Apache/nginx) in front | `1` — or the proxy's address, e.g. `127.0.0.1` when it runs on the same host | The proxy appends the real client to X-Forwarded-For; only that last entry is believed. |
| C. Managed platform / load balancer with known addresses | the platform's proxy CIDRs, e.g. `10.0.0.0/8` (or its documented hop count) | Only requests arriving from those addresses may set forwarded headers. |

Never trust everything (`true`, `*`, `all` are refused): any client could then pick its own IP and escape the login
limiter. Too few hops is also wrong: every user then shares the proxy's IP, so 10 bad logins lock everyone out. Too many
hops lets a client prepend fake addresses. Behind an https proxy the proxy must send `X-Forwarded-Proto: https`
(the reference configurations do).

## 9. Web security headers — who owns what

| Header | Web (`/`, `/assets/*`) | API (`/api/*`) |
|---|---|---|
| Content-Security-Policy | proxy: `default-src 'self'; script-src 'self'; style-src 'self'; …; frame-ancestors 'none'` | API: `default-src 'none'; frame-ancestors 'none'; …` |
| X-Content-Type-Options, X-Frame-Options, Referrer-Policy, Permissions-Policy, COOP | proxy | API |
| Strict-Transport-Security | **proxy** (TLS vhost only; never on plain http) | API sends the same value in production; the proxy's replaces it |
| Cache-Control | proxy: `index.html` and client routes `no-cache`; `/assets/*` `public, max-age=31536000, immutable` | API: `no-store` on every response (downloads `private, no-store`) |

The single source of these values is [deploy/security-headers.json](../deploy/security-headers.json). The policy is
`'self'` only — no `'unsafe-inline'`, no `'unsafe-eval'`, no external host. Verified in Task 46 against the built bundle
behind the reference proxy: 75 page visits across HR Admin, Employee and Executive on real data (including the
organization tree with 150+ styled nodes) produced no violation — React applies `style` props through the CSSOM, which
CSP does not restrict, and Zod runs `jitless` (apps/web/src/zod-config.ts) so its `new Function` probe never fires.
A split-origin deployment (web and API on different hosts) must add the API origin to `connect-src`.

Verify the live deployment after every change of proxy configuration:

```sh
npm run ops:verify-web -- https://hr.example.com
```

It checks the HTML shell, a client-side route, a hashed asset, a missing source map (404) and the API through the proxy.

## 10. Start, restart, health

```sh
ENV_FILE=/etc/hr-platform/api.env npm start      # = NODE_ENV=production node apps/api/dist/server.js
npm run ops:check                                 # liveness + readiness, exit 0/1 (ENV_FILE set)
```

`npm start` always runs production mode from the built files — it never starts Vite or a watcher. Run it under a
process supervisor that restarts it — reference unit `deploy/systemd/hr-api.service` (`Restart=on-failure`, crash-loop
limit, `OnFailure` alert hook) or a container restart policy: the process exits on a fatal error (`app_fatal_error`). SIGTERM drains in-flight requests (10 s) and disconnects the database. Probes: `/api/v1/health/live`
(process), `/api/v1/health/ready` (database + document storage; 503 when not ready) — unauthenticated, not
rate-limited, `no-store`.

## 11. Backups and monitoring (Task 49)

```sh
install -d -m 700 -o hr /var/backups/hr                      # BACKUP_DIR, on a different volume than the database
# /etc/hr-platform/backup.env (root-owned, 0600): BACKUP_DIR, BACKUP_OFFHOST_COMMAND/_VERIFY_COMMAND, hook settings
cp deploy/systemd/hr-backup.* deploy/systemd/hr-monitor.* deploy/systemd/hr-alert@.service /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now hr-backup.timer hr-monitor.timer
npm run ops:backup && npm run ops:restore -- "$BACKUP_DIR"/hr-backup-* --verify-only   # first set + restore drill
npm run ops:monitor-check
```

Off-host hooks: `deploy/backup/` (rsync over SSH or rclone). Alert delivery: replace `/usr/local/bin/hr-notify` in
`hr-alert@.service` with your integration, and add an external HTTPS uptime monitor on `/api/v1/health/live` and
`/api/v1/health/ready`. Nothing pages anybody until that is done. Details: [backup-restore.md](backup-restore.md),
[operations-monitoring.md](operations-monitoring.md). Before each new release: `npm run ops:preflight`.

## 12. Checklist

- [ ] PostgreSQL database + dedicated role; credentials only in the secret store / env file
- [ ] Env file outside the repository, `chmod 600`, `NODE_ENV=production`, every P variable set
- [ ] `DOCUMENT_STORAGE_DIR` persistent, mode 0700
- [ ] `npm ci && npm run build` succeeded on this exact commit/tag
- [ ] `npm run db:deploy` succeeded
- [ ] First install only: `npm run bootstrap:admin`
- [ ] Reverse proxy from `deploy/` with TLS; HTTP redirects to HTTPS
- [ ] `TRUST_PROXY` matches the topology (§8)
- [ ] `npm run ops:verify-web -- https://<host>` passes
- [ ] `npm start` under a supervisor; `npm run ops:check` passes
- [ ] `backup.env` with `BACKUP_DIR` and verified off-host hooks; `hr-backup.timer` and `hr-monitor.timer` enabled
- [ ] First `npm run ops:backup` exit 0; `ops:restore -- <set> --verify-only` exit 0 (restore drill)
- [ ] `npm run ops:monitor-check` exit 0
- [ ] Alert delivery configured (`hr-alert@.service` → your pager/chat/e-mail) and an external uptime monitor on
      `/health/live` + `/health/ready` — **the application cannot do this part for you**
- [ ] PostgreSQL disk/availability alerts on the database host or provider
